Create `src/ml/gpu_runtime.nim` with GPU detection and runtime configuration.

Define types:
- `GpuBackend` enum: `CPU = "cpu"`, `CUDA = "cuda"`, `CoreML = "coreml"`
- `GpuRuntime` object: `backend: GpuBackend`, `available: bool`, `deviceName: string`

Implement `detectGpu*(): GpuRuntime`:
- On Linux (`when defined(linux)`): Try to detect CUDA by checking if `libcudart.so` or `libnvcuda.so` exists via `dynlib` loading or file existence check at common paths (`/usr/local/cuda/lib64/`, `/usr/lib/x86_64-linux-gnu/`). Do NOT hard-link CUDA -- just check availability. If found, return CUDA backend.
- On macOS (`when defined(macosx)`): CoreML is always available on macOS 10.15+. Return CoreML backend. Use `when defined(macosx)` compile-time check since we only target recent macOS.
- On Windows (`when defined(windows)`): Always return CPU backend (ML features are stubbed on Windows).
- Fallback: Return CPU backend with `available: false`, `deviceName: "CPU"`.

Implement `logBackend*(runtime: GpuRuntime)`:
- Log which backend is active using the project's `log` module pattern: `echo "[gpu] Using backend: {runtime.backend} ({runtime.deviceName})"`

Follow established FFI patterns from `src/ml/onnx.nim`:
- Use `when defined(windows)` for stub implementations
- Keep all platform-specific code behind `when defined()` guards
- No hard dependencies on GPU libraries -- detection only, no linking

Do NOT use `{.dynlib.}` pragmas or link against CUDA/CoreML. This module only detects availability; the actual provider loading happens in ONNX Runtime (Plan 15-01, Task 2).

<task type="auto">
  <name>Task 2: Extend ONNX wrapper with execution provider support</name>
  <files>src/ml/onnx.nim</files>
  <action>
Extend `src/ml/onnx.nim` to support creating sessions with GPU execution providers.

In the `else` block (Linux/macOS implementation):

1. Add ONNX Runtime C API bindings for execution providers to the `OrtApi` type:
   - `CreateSessionOptions*: proc(options: ptr pointer): ptr OrtStatus {.cdecl.}`
   - `ReleaseSessionOptions*: proc(options: pointer) {.cdecl.}`
   - `SessionOptionsAppendExecutionProvider_CUDA*: proc(options: pointer, cudaOptions: pointer): ptr OrtStatus {.cdecl.}`
   - `CreateCUDAProviderOptions*: proc(options: ptr pointer): ptr OrtStatus {.cdecl.}`
   - `ReleaseCUDAProviderOptions*: proc(options: pointer) {.cdecl.}`

   Note: The ONNX Runtime C API provides these via the OrtApi function table. The exact API functions are:
   - `OrtSessionOptionsAppendExecutionProvider_CUDA_V2` for CUDA
   - For CoreML, use `OrtSessionOptionsAppendExecutionProvider_CoreML` (available in onnxruntime_c_api.h)

   Since we use the OrtApi function table pattern (v14+), add the corresponding function pointers. Check the actual C API header at `build/include/onnxruntime/core/session/onnxruntime_c_api.h` for exact signatures.

2. Add `OrtSessionOptions` type:
   ```nim
   OrtSessionOptions* = object
     handle: pointer
   ```

3. Add `createSessionOptions*(): OrtSessionOptions` proc that creates default session options.

4. Add `loadModelWithProviders*(env: OrtEnv, modelPath: string, backend: string): OrtSession` proc:
   - Creates session options via `CreateSessionOptions`
   - Based on `backend` parameter:
     - `"cuda"`: Try `SessionOptionsAppendExecutionProvider_CUDA`. Wrap in try/except -- if it fails (CUDA not installed, wrong version), log warning and proceed without CUDA (CPU fallback happens automatically since ONNX Runtime always has CPU as last provider).
     - `"coreml"`: Try appending CoreML provider. Same try/except fallback pattern.
     - `"cpu"`: No provider append needed, default is CPU.
   - Creates session with options: `CreateSession(env.handle, modelPath.cstring, options.handle, addr sessionHandle)`
   - Returns OrtSession
   - Defer cleanup of session options

5. Update existing `loadModel` to remain unchanged (backward compatible -- creates session without options, CPU only).

6. In the Windows stub block, add stub `loadModelWithProviders` that raises `OrtError` (same pattern as existing stubs).

IMPORTANT: The ONNX Runtime execution provider API functions may not be directly in the OrtApi function table for all providers. Some providers (CUDA, CoreML) use standalone C functions rather than function table entries. Check the header file. If they are standalone functions:
- For CUDA: `OrtSessionOptionsAppendExecutionProvider_CUDA_V2` is a standalone function, import with `{.importc, header: "onnxruntime_c_wrapper.h".}`
- For CoreML: `OrtSessionOptionsAppendExecutionProvider_CoreML` is a standalone function

The key insight: these provider functions may or may not be available at link time depending on how ONNX Runtime was built. Use `when defined(linux)` for CUDA provider function, `when defined(macosx)` for CoreML provider function. If the function is not available at link time (because ONNX RT was built without that provider), the linker will fail -- this is acceptable because the build system controls which providers are available.

Alternative safer approach: Use `dynlib` to load provider functions at runtime, or simply use the `SessionOptionsAppendExecutionProvider` generic function if available in the API version we target.
