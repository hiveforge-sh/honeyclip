Purpose: 4K BGR frames are ~25MB each. Without pooling, per-frame allocation causes fragmentation and overhead. Without bounded decode queues, decoded frames accumulate faster than they're consumed, causing OOM on long videos. Fulfills MEM-01, MEM-02.

  <name>Task 1: Create frame buffer pool module</name>
  <files>src/ml/buffer_pool.nim</files>
  <action>
Create `src/ml/buffer_pool.nim` implementing a pre-allocated frame buffer pool.

Define types:
```nim
type
  FrameBuffer* = object
    data*: ptr UncheckedArray[uint8]
    capacity*: int       # Total bytes allocated
    width*: int
    height*: int
    channels*: int
    inUse*: bool

  BufferPool* = object
    buffers*: seq[FrameBuffer]
    maxBuffers*: int
    frameSize*: int      # bytes per frame (width * height * channels)
    acquiredCount*: int  # Track how many buffers are currently in use
```

Implement:

1. `newBufferPool*(width, height, channels: int, maxBuffers: int = 16): BufferPool`
   - Pre-allocate `maxBuffers` frame buffers
   - Each buffer: `width * height * channels` bytes
   - Use `alloc` for raw memory allocation (not GC-managed -- these are large buffers)
   - For 4K BGR: 3840 * 2160 * 3 = 24,883,200 bytes (~24MB per buffer)
   - Pool of 16 = ~400MB (configurable via maxBuffers)
   - Log pool creation: "Buffer pool: {maxBuffers} x {frameSize/1024/1024:.1f}MB = {total:.0f}MB"

2. `acquire*(pool: var BufferPool): ptr FrameBuffer`
   - Find first buffer where `inUse == false`
   - Mark as `inUse = true`, increment `acquiredCount`
   - Return pointer to the FrameBuffer
   - If all buffers in use, return `nil` (caller handles -- either skip frame or wait)

3. `release*(pool: var BufferPool, buffer: ptr FrameBuffer)`
   - Set `buffer.inUse = false`, decrement `acquiredCount`
   - Assert buffer belongs to this pool (check pointer range)

4. `available*(pool: BufferPool): int`
   - Return `pool.maxBuffers - pool.acquiredCount`

5. `=destroy*(pool: var BufferPool)`
   - Free all allocated frame buffers via `dealloc`
   - Set all data pointers to nil

6. `resize*(pool: var BufferPool, width, height, channels: int)`
   - If new frame size differs from current, reallocate all buffers
   - Assert no buffers are currently in use (acquiredCount == 0)
   - Useful when switching between videos of different resolutions

Follow patterns from existing codebase:
- `=destroy` with var parameter (established in src/ml/onnx.nim, src/ml/opencv.nim)
- `alloc`/`dealloc` for raw memory (established in src/ml/facedetect.nim)
- Use `result.field = value` pattern, not `return Type(...)` (Nim 2.x destructor pattern)

This module does NOT use threads or locks. The current face detection pipeline is single-threaded (see facesPipeline iterator in faces.nim). If threading is added later, locks can be added to acquire/release.

<task type="auto">
  <name>Task 2: Add bounded decode queue to face detection pipeline</name>
  <files>src/analyze/faces.nim</files>
  <action>
Modify `src/analyze/faces.nim` to implement a bounded decode queue that prevents OOM on long/large videos.

Changes:

1. Add `maxQueueFrames` parameter to `FaceAnalysisParams`:
   ```nim
   maxQueueFrames*: int    # Max decoded frames in memory (default 30)
   ```
   Update the default in the `faces*` proc signature to `maxQueueFrames: 30`.

2. Add `maxQueueFrames` to `toCacheArgs` so changing the queue size doesn't serve stale cache (it shouldn't affect detection results, but include it for safety since different queue sizes could theoretically cause different frame sampling if frames are skipped).

3. In the `facesPipeline` iterator, add frame counting logic:
   - Track the number of currently "active" (decoded but not yet consumed by caller) frames
   - The existing pipeline already processes frames one at a time in the `for` loop -- the issue is that `avcodec_receive_frame` can decode multiple frames per packet, and FFmpeg's internal decode queue can grow unbounded
   - Add a frame counter that tracks decoded frames awaiting processing
   - If the count exceeds `maxQueueFrames`, skip decoding additional packets until the consumer catches up (this is the backpressure mechanism)

   In practice, since the `facesPipeline` iterator yields one frame at a time and the caller processes synchronously, the actual concern is about FFmpeg's internal buffer. The bounded decode approach here is:
   - Add a `decodedFrameCount` counter in the pipeline
   - Every N frames (where N = maxQueueFrames), call `av_frame_unref` on the filtered frame immediately after yielding, ensuring frames don't accumulate
   - More importantly: track total memory used and log a warning if it exceeds expected bounds

4. Add memory tracking to the `faces*` proc:
   - Before the processing loop, calculate expected peak memory: `maxQueueFrames * targetHeight * (targetHeight * 16/9) * 3` (since frames are scaled to targetHeight before detection)
   - Log: "Face detection: max {maxQueueFrames} frames in memory (~{peakMB:.0f}MB)"

5. Important: The current pipeline already processes frames sequentially (decode -> filter -> yield -> process -> unref -> next). The main OOM risk is from the RESULT accumulation (`result.add(FrameFaces(...))`) growing unbounded for very long videos. For a 1-hour video at 1fps sampling, this is ~3600 FrameFaces entries -- small enough (~few MB). The bounded decode queue primarily protects against the decode-ahead problem.

6. Also add `import ../ml/buffer_pool` and integrate buffer pool usage:
   - Create a BufferPool at the start of `faces*` proc, sized to the targetHeight resolution (not full 4K, since frames are scaled down before face detection)
   - Use `pool.acquire()` before calling `detectFaces` to get a stable buffer
   - Copy the filtered frame data into the pooled buffer via `copyMem`
   - Call `detectFaces` on the pooled buffer data
   - `pool.release()` after detection completes
   - This prevents per-frame allocation in the hot loop
   - Pool size: 4 buffers is sufficient since processing is sequential (only 1 buffer in use at a time, extras handle pipeline latency)

   Actually, re-examining the code: `detectFaces` in faces.nim calls `facedetect.detect(imageData, width, height, stride)` which internally allocates its own result buffer and returns `seq[FaceRect]`. The input `imageData` comes from the FFmpeg filtered frame (`frame.data[0]`), which is managed by FFmpeg's frame allocation. So the buffer pool benefit here is marginal for the detection input.

   The buffer pool is more relevant for the FULL resolution frame when we add GPU-based ONNX face detection (Plan 15-01). For now, integrate the buffer pool type but make its usage optional/preparatory:
   - Import buffer_pool
   - Add a comment block showing where buffer pool will be used when ONNX face detection replaces libfacedetection for GPU path
   - Do NOT force buffer pool usage into the current libfacedetection path (it uses FFmpeg's frame buffers, which are already managed)
  </action>
